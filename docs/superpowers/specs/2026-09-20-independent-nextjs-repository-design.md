把已完成的首页、Products、M350 静态应用独立管理，摆脱旧 WordPress 仓库的代码及发布配置。D23 负责内容和文案，D32 负责实现与发布。用户本轮明确告知 Gate9 已通过，沿用该结论，不重新要求页面验收；不编造未提供的验收回执或版本绑定。

已比较同仓库改名分支与独立仓库：前者仍共享旧项目管理与工作流，用户选择后者。新仓库采用一次可追溯快照导入，不改写旧历史；完整旧历史保留在原仓库，迁移记录注明来源 SHA 及逐文件校验值。

## 本地目录与迁入范围

建议目录 `D:/32NextJS`，核查时不存在。若执行时已存在，不覆盖、不混入其他文件，先核实归属。

## Git 初始化与正常流程

新仓库拥有独立 .git，不是旧仓库的 worktree。先在本地 develop 创建仅含治理文档的初始化提交，并从此建立本地 main 起点。随后从 develop 创建 `codex/standalone-nextjs-import` 实现迁移；完成校验后合入本地 develop，对实际候选运行集成验证。全部通过后将本地 main 快进到同一 SHA；失败则保持 main 原位，修复后重新验证。

这次初始化完成后 develop/main 指向同一已验证的静态站提交。以后功能分支从本地 develop 创建并合回；本地集成通过才快进 main。功能分支与 develop 不常规推送，只有 main 是未来常规发布入口。

旧仓库所有已有分支、worktree、数据库、媒体和线上站点不变。本设计文件及其计划留在当前设计分支作为迁移记录，不合入旧 develop/main。

## 验证与交付

对所有迁入应用源码、内容、资产、测试及 lockfile，比较来源 Git blob/字节校验；允许的差异仅为迁移所需的 README 链接和新增治理文档，并在清单列明。完整安装依赖，运行 typecheck、静态 build 和现有 37 项浏览器测试，验证在新目录可独立构建，无旧目录运行依赖。测试继续使用 loopback 8333；占用时不得停止他人的服务。

旧页面 Gate9 结论不重做；本次测试验证迁移与集成，不声称重新取得独立验收。历史偶发样式断言异常保留，新失败调查原因，不忽略失败。新的验证记录写入独立目录，不覆盖原有截图和回执。

完成标准：新目录为独立 Git 仓库；develop/main 同 SHA；源码迁移可追溯；全部适用检查通过；无远端绑定、推送或线上变更。交付新路径、提交、验证结果与剩余发布依赖。

## 发布边界

本轮不创建 GitHub 仓库、不设置 origin、不推送、不配置未知托管平台。后续确定远端仓库及静态托管目标后，再建立 main 自动测试、静态制品部署和回滚流程，验证后执行生产切换。新仓库建立不等于上线，也不沿用旧 WordPress 自动发布。
